Pluggable Monolith

How to start a product today as one codebase, with Python behind and Next.js in front, whose modules and vendors can be added, swapped or removed without touching the rest. And what generative AI changes about that design.

GoalAdding, swapping or removing a module or a vendor touches that module and one line of wiring.
AchievableChange costs in proportion to its size. Removing a module is a config line plus dropping its schema.
Not achievableZero rework. Contracts still evolve, and some swaps, such as embedding models and prompts, leak through any interface.
ProofBoundary contracts and a deletion test run in CI on every commit (§7). If they pass, the claim holds.

1The answer on one page

Build a modular monolith. One repository and a few processes (web, API, workers) hold many modules. Each module owns one business capability and its data, and other code reaches it only through its published contract. Every external dependency, the LLM included, sits behind an interface the core owns. Tools check the boundaries in CI, and the proof that a module is pluggable is a test that removes it and expects everything else to pass.

2The atoms

Eight rules generate most of the choices in this document. The first four decide where boundaries go; the last four keep them real.

Hide the decisions likely to change

Parnas's criterion from 1972 still decides where boundaries go: list the design decisions that may change, and make each module the only place that knows one of them. A module is not a step in a flowchart or a layer of technology.

Source: Parnas, “On the criteria to be used in decomposing systems into modules”, CACM 15(12), 1972.

Depend on interfaces you own

The core declares the port it needs, in its own terms, and adapters translate each vendor to it. Dependencies point inward, so swapping a vendor never edits the core.

Source: Cockburn, Hexagonal architecture (2005). In lab 01, switching vendor without a port changed 21 lines across two core functions.

Balance coupling; don't just minimise it

Coupling has three dimensions: how much knowledge two parts share, how far apart they are, and how often they change. Sharing a lot is fine up close; sharing little is fine far apart; and anything is fine if it never changes. Pain comes from sharing a lot, at a distance, on something volatile.

Source: Khononov, Balancing Coupling in Software Design (2024). His formula: balance = (strength XOR distance) OR NOT volatility.

Every seam has a price

An interface adds a second place to read, a mapping to maintain, and a contract that drifts toward the lowest common denominator of its vendors. An interface with one implementation that nobody will replace is speculative generality. “Everything pluggable” is its own kind of rework; put seams on the volatile axes only.

This is the correction to “zero rework by design”: the target is change in proportion to its size, not no change.

A module owns a capability, its data and its contract

A module has a provided interface (the API and events it publishes), internals nobody else touches, and a required interface (the APIs it calls, the events it reacts to, the configuration it takes). Its tables are internals. Other modules pass IDs and data objects across the line, never live ORM objects.

Source: the clearest definition is Spring Modulith's application module. The idea carries over to any language.

Enforce boundaries by machine

Boundaries that live only in people's heads erode, and coding agents erode them faster. Import contracts that fail the build hold the line. For code that already breaks them, list the known violations and make CI allow no new ones.

Evidence: Kraken (2023): over 40 import-linter contracts, ignored imports tracked as debt. Hu et al. (2026), benchmarking agents that build CLI tools from scratch: agents “exhibit a strong tendency to generate monolithic code structures”.

Prove it with running code

Static checks see imports, not behaviour. The test of pluggability is to remove a module and run everything else. If that passes, the module was pluggable; if it doesn't, the failure shows exactly where the hidden coupling is.

Source: Shopify's Packwerk retrospective (2024): “running code, more than any metric, will always be the best indicator of real progress.”

Use standards as free ports

Where an open standard exists, it is already the interface and every vendor is already an adapter: OIDC for identity, OpenAPI for HTTP, OpenTelemetry for telemetry, OpenFeature for flags, CloudEvents for event envelopes, MCP for tools, A2A for agents.

Status: CloudEvents graduated in CNCF (2024-01-25); OpenFeature is incubating (since 2023-11-21); MCP and A2A are Agentic AI Foundation projects.

3System at a glance

Three processes are built from one codebase. The web app and the API meet at a generated contract. Modules meet each other only through public APIs and events, and reach the outside world only through ports in a small kernel.

Repository layout

product/
├─ apps/
│  ├─ api/          FastAPI composition root: loads the enabled modules
│  ├─ worker/       the same modules, background entry point
│  └─ web/          Next.js 16: routes and composition only
├─ modules/         one uv workspace member per business capability
│  ├─ catalog/
│  ├─ orders/
│  ├─ billing/
│  └─ assistant/    an AI feature is a module like any other (§10.3)
├─ kernel/          ports and plumbing only: db, bus, outbox, identity, flags,
│                   telemetry, model gateway. No business code, ever.
├─ packages/        the TypeScript workspace
│  ├─ api-client/   generated from contracts/openapi.json
│  ├─ ui/           design system
│  └─ features/     one package per frontend feature, mirroring the modules
├─ contracts/       generated OpenAPI and event schemas, checked in and diffed
├─ pyproject.toml   uv workspace root, import-linter contracts
├─ pnpm-workspace.yaml · turbo.json
└─ AGENTS.md        repository rules; each module adds its own AGENTS.md

The kernel is the part most likely to rot. It holds interfaces and plumbing that every module needs and nothing that belongs to one of them. A “common” or “utils” package that grows domain code turns into the dependency everyone shares, and then nothing can be removed.

4Anatomy of a module

A module is the unit you add or remove. It is a package with one front door, and everything behind that door is private.

5How modules talk

There are four ways across a module line. Pick by what you need to happen when the other side is removed.

StyleUse it toCouplingIf the other side is removed
Public API callAsk a question you need answered inside this requestExplicit: a typed function signature, declared as a dependencyThe build fails. That's correct: it was a real dependency
Domain event, in processTell others a fact; they decide what to doWeak: the publisher doesn't know its subscribersIts handlers vanish; the publisher is unaffected
Outbox, then brokerTell a fact that must survive a crash, or reach another processWeak and durableAs for events, plus the ability to replay
HTTP with OpenAPICross a process line: web to API, or to an extracted moduleA contract, over the networkGenerated types and contract tests catch it
  • Ask with calls, tell with events. A module must never wait on another module's event to finish its own transaction.
  • Write events to an outbox table in the same transaction as the change. A relay then publishes them, in process at first and to a broker later. The outbox is what makes “publish if and only if the change committed” true (transactional outbox).
  • Keep the dependency graph acyclic and declared. Each dependency is listed in the module's pyproject.toml and allowed by an import contract. A cycle means two modules are really one, or a third is missing.
  • Version events like APIs. Add fields; never repurpose one. Use a CloudEvents envelope once events leave the process.

6Data ownership

Most modular monoliths fail here, not in the code. A shared table is a shared internal, and no import linter can see it.

  • One Postgres, one schema per module. Each module keeps its migrations in its own Alembic version directory. Alembic supports this directly: “if an application is organized into several sub-modules, each one would have a version directory containing migrations pertinent to that module” (Working with Multiple Bases).
  • No joins or foreign keys across schemas. To read another module's data, call its API or keep a local read model fed by its events.
  • Optional hard wall: give each module a database role that can touch only its own schema. A cross-module query then fails at runtime instead of passing review.
  • Removing a module means disabling it, exporting what you must keep, and dropping its schema. Nothing else references it.
  • Vectors, blobs and caches are ports too. Start with what Postgres and S3-compatible storage give you; the adapter changes when the numbers demand it.

The deletion test

For each optional module, in CI:

  1. Remove it from ENABLED_MODULES, or delete its folder and its one registration line.
  2. Boot the API and the worker.
  3. Run the import contracts, the type checks and every other module's tests.
  4. Build the web app without its feature package.

If all four pass, the module is removable, and the claim in the header holds for it. A failure points at the hidden coupling. The test also marks which modules are core: those are the ones whose removal is allowed to fail the build.

uv gives the whole workspace one environment, so a module can import a package it never declared and the code still runs until the day it's extracted. That is why deptry sits next to import-linter. The uv docs say workspaces don't suit members that need “a separate virtual environment for each member”.

8Composition and plugins

Pluggability needs one place where modules are switched on. That place is the composition root: the only code that knows which modules and adapters exist. Modules can be switched at three points, each with its own mechanism.

WhenMechanismRemovalUse for
BuildWorkspace membership in uv and pnpmDelete the member and its registration lineModules that are part of the product
BootA config list, or Python entry points discovered with importlib.metadataTake it out of ENABLED_MODULESEditions, per-customer deployments, optional integrations
RunOpenFeature flagsFlip the flagGradual rollout, kill switches, experiments
 
# kernel/modules.py: the one interface every module implements
class Module(Protocol):
    name: str
    def register(self, app: FastAPI, kernel: Kernel) -> None: ...

# apps/api/main.py: the composition root
def create_app(settings: Settings) -> FastAPI:
    app = FastAPI()
    kernel = Kernel.from_settings(settings)   # builds every adapter
    for module in discover("product.modules", settings.enabled_modules):
        module.register(app, kernel)          # routers, handlers, tools
    return app
# modules/billing/pyproject.toml: how a module announces itself
[project]
name = "billing"
dependencies = ["kernel", "catalog"]

[project.entry-points."product.modules"]
billing = "billing.module:BillingModule"

[tool.uv.sources]
kernel = { workspace = true }
catalog = { workspace = true }

Entry points are the Python packaging standard for plugin discovery (packaging guide). The same mechanism lets a module live outside the repository later, installed as a package, with no change to the root.

Dependency injection: the composition root is a pattern, not a framework. create_app() builds adapters from config and hands them to modules, and FastAPI's Depends covers per-request wiring. Add a container such as dishka 1.10, svcs 26.2 or wireup 2.12 only when the object graph no longer fits on a page.

9Next.js as a composition shell

The same rules apply in front. Next.js “is unopinionated about how you organize and colocate your project files” (project structure docs), so the module boundaries must come from you.

apps/web/
├─ app/(shop)/orders/page.tsx   composes @product/features-orders; nothing else
├─ app/api/chat/route.ts        streams from the Python agent
├─ proxy.ts                     auth redirects (middleware.ts before Next.js 16)
└─ features.config.ts           the list of enabled features: the web composition root
packages/features/orders/
├─ index.ts                     client-safe public API
├─ index.server.ts              server-only exports, such as data loaders
├─ manifest.ts                  the nav entries, routes and flags it contributes
└─ _internal/                   components and hooks nobody else imports
  • Routes compose; features implement. A page imports from feature packages and passes data down. The navigation is built from the enabled features' manifests, so removing a feature is one line in features.config.ts plus its route folder.
  • Split each feature's public API by environment. Feature-Sliced Design's Next.js guide explains why: “If a server-only module is exported from index.ts, server-only side effects can propagate into the client module graph when a Client Component imports that slice” (FSD with Next.js).
  • Next.js is the backend for the browser. Server Components call the generated client on the server, holding the session and keeping tokens out of the browser. Client components go through route handlers or server actions. proxy.ts replaced middleware in Next.js 16 and defaults to Node.js, but the docs warn against relying on it alone: check authorisation inside each server function, and in the API behind it (proxy).
  • Feature-Sliced Design or plain features? FSD gives a ready-made layer rule (app → pages → widgets → features → entities → shared) and a linter. Plain feature packages that mirror the backend modules are simpler. Start plain; adopt FSD's layers when many widgets start combining several features.
  • No micro-frontends inside a monolith. If separate teams later need separate deploys, Next.js multi-zones split the site by path into independent apps (multi-zones).

10The GenAI plane

Generative AI adds no new architectural principle. It applies the same ones under much more pressure: the model is the most volatile dependency a product has ever had, and it is also non-deterministic, slow, expensive per call and open to manipulation through its input.

10.1What AI changes

ForceWhat it does to the design
ChurnThe model sits behind an alias and a gateway, so a swap is config plus an eval run. Pydantic AI keeps its v2 core small for this reason: “the field moves fast enough that committing further out means committing to decisions that fit today and not the world three months from now” (2026-06-23).
Non-determinismEvals replace exact-match tests as the check on AI modules, and traces become the debugger.

10.2Model plane: aliases, gateway, router

Three different things get called a “model router”. Keep them apart so each can change alone.

  • Aliases are the atom. Both ecosystems support them: AI SDK 7's customProvider and createProviderRegistry map friendly names to models (docs), and Pydantic AI has provider-prefixed model names and a FallbackModel that also falls back on response conditions (docs).
  • The gateway is a separate process. It holds every provider key, enforces per-tenant budgets and rate limits, and logs every call. LiteLLM (SDK and proxy, 100+ providers) and agentgateway (Linux Foundation; proxies LLM, MCP and A2A traffic) are open-source options; hosted gateways are adapters too.
  • Start with static routing. RouteLLM reported cutting costs “by over 2 times in certain cases” without losing quality (2024, self-reported). But LLMRouterBench, 400K+ instances across 33 models, found that “many routing methods exhibit similar performance under unified evaluation, and several recent approaches, including commercial routers, fail to reliably outperform a simple baseline” (2026-01-12). A 2026 survey notes that “practical systems are often compositional” (Moslem and Kelleher). So route by task with a fallback chain, measure, and add a learned router only when your own evals show it wins.
  • What an alias can't hide. Embeddings: changing the model means re-embedding the corpus, because vectors from different models aren't comparable (lab 01's two toy vendors share a vector length but not a space). Prompts are tuned to a model, so every alias change reruns the evals. Capabilities differ, including tool calling, structured output, context length and reasoning controls. Price and latency profiles differ too.
  • The gateway is a prime target. On 2026-03-24, litellm 1.82.7 and 1.82.8 were published to PyPI with a credential stealer and were live for about 40 minutes. The maintainers believe the attack came through a dependency in their CI, and users of the official proxy Docker image, which pins its dependencies, were not affected (LiteLLM). Run the gateway as a pinned image in its own process holding only its own secrets, install by hash (uv.lock records hashes), and keep it behind your port so it can be replaced.

10.3AI features as modules

  • An assistant is a module like any other. Its tools are the tools.py faces of other modules: thin wrappers over their public APIs, called with the end user's identity. The agent can do only what the API allows that user to do, and removing a module removes its tools.
  • Protocols at the edges, not inside. MCP exposes tools to agents outside the product; the current spec is 2026-07-28, which negotiates the version on each request and adds a server/discover call (versioning). A2A reached v1.0 in March 2026 and joined the Agentic AI Foundation on 2026-08-17; use it only when other systems' agents delegate whole tasks to yours (AAIF). AG-UI standardises agent-to-UI events (AG-UI). Inside one process, a function call beats any protocol.
  • The frameworks follow the same pattern. Pydantic AI v2 keeps a small core and moves memory, guardrails and context management into capabilities and a separate Harness package. AI SDK 7 (2026-06-25) adds WorkflowAgent for durable agents and HarnessAgent for running Claude Code, Codex or Pi behind the same UI hooks. Treat the framework as an adapter as well: keep its types inside the assistant module.
  • Reusable agent know-how is a plugin. Agent Skills, a SKILL.md folder that an agent loads only when a task needs it, is an open format that started at Anthropic and is now supported by many agent products (agentskills.io).
  • Start simple. “Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short” (Anthropic, 2024-12-19). Routing is one of the workflow patterns listed there.

10.4Long-running work

Agents that run for minutes or days, wait for a person, or call unreliable tools need their progress checkpointed so a restart resumes instead of repeating. Pydantic AI v2 ships durable execution on Temporal, DBOS and Prefect, and Restate integrates through its own SDK (docs). DBOS is a library that checkpoints workflows to Postgres, in Python, TypeScript, Go and Java (DBOS), so a monolith gets durability without new infrastructure. Temporal is the stronger choice once workflows cross many services or teams. Run a bake-off with your own workloads before committing to either.

10.5Evals and tracing

  • Evals are the tests for AI modules: a dataset of cases plus scorers, run in CI on every prompt, model or alias change, with thresholds that fail the build.
  • Traces follow OpenTelemetry. The GenAI semantic conventions cover model, agent and MCP spans, but their status is still Development (repo), so pin a version. Observability products are then adapters behind OTel, and AI SDK 7 rebuilt its telemetry around one integration system.
  • Close the loop: failures found in production traces become new eval cases.

10.6Security

  • Authorise at the module API, not in the prompt. Tools call APIs as the end user, so a manipulated model can't exceed that user's rights.
  • Scope context per tool. AI SDK 7's typed tool context is “limited to the tool to prevent 3rd-party tools from accessing context they do not need” (AI SDK 7).
  • Require approval for side effects. Durable workflows make approval a step that can wait.
  • Treat model output as untrusted input. Prompt injection has no complete fix, so design for containment: least privilege, approvals and audit logs.

11Scale and extraction

A modular monolith scales out as it is: stateless API replicas behind a load balancer, workers pulling from queues, and Postgres scaled up, then out with replicas. You extract a module only when a trigger fires:

  • its scaling profile differs sharply, for example it needs GPUs;
  • a separate team needs its own release cadence;
  • its failures must not take down the rest;
  • it needs a different runtime or language.

Extraction is then mechanical. The port stays the same, and its adapter changes from an in-process call to an HTTP or queue client. Events already flow through the outbox and the schema already belongs to the module, so callers don't change.

A framework is no substitute for the pattern. Google's Service Weaver let teams write one modular binary and deploy it as services. It entered maintenance mode on 2024-12-05 and has since been archived, because “it was hard for users to adopt Service Weaver directly since it required rewriting large parts of existing applications” (repo notice).

The research base is thin. The first systematic review of modular monoliths found only 15 primary studies, and lists “the absence of consensus on a clear comprehensive definition, limited empirical benchmarking, and insufficient tools support” as the main gaps (Al-Qora'n and Al-Said Ahmad, 2025-10-29). An earlier grey-literature review drew on 64 practitioner sources (Su and Li, 2024). Most of what is known comes from practitioners' experience at companies such as Shopify and Kraken, and from the Spring Modulith project.

14Where to start

Most of the value comes from the first six concepts, marked below. The rest applies them. The ordered list, with progress, lives in the topic map.

  1. Where seams go. Information hiding and balanced coupling decide what deserves an interface (§2).
  2. Ports and adapters. The mechanism behind every swap; lab 01 already started it (§2).
  3. Module anatomy. A public API, private internals and owned data (§4, §6).
  4. Enforcement and the deletion test. Boundaries that fail the build (§7).
  5. Composition root and plugins. Removal as one line (§8).
  6. The model plane. Aliases, a gateway, routing, and what an alias can't hide (§10.2).
  7. Module communication. Calls, events and the outbox (§5).
  8. Contract-first frontend. Next.js feature modules on a generated client (§9).
  9. AI features as modules. Tools over module APIs, with MCP, AG-UI and A2A at the edges (§10.3).
  10. Evals and tracing. How you know a model or prompt swap is safe (§10.5).
  11. Durable execution. Long-running agents and approvals (§10.4).
  12. Extraction. Moving a module out without touching its callers (§11).

15Open questions

Each has a recommendation; the owner decides.

  1. FastAPI or Django? Recommend FastAPI, because Pydantic runs through the whole stack, from HTTP to events to LLM output. Switch to Django 6.1 with Django Ninja if the product is mostly back-office CRUD and admin screens.
  2. Where do agents live? Recommend Python, next to the modules and data, streaming to Next.js over the AI SDK protocol or AG-UI. Switch if the team is mostly TypeScript.
  3. Lab 01's home. Lab 01 (ports and adapters) is general, and it is concept 2 here. Recommend finishing it as this topic's first lab while context engineering keeps linking to it; one lab and one note serve both maps.
  4. Lab domain. Recommend a tiny shop (catalog, orders, billing, assistant): small enough to build fast, and rich enough for calls, events, a vendor port and an AI module.
