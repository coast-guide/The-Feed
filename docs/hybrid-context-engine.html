High-level design · draft for discussion · evidence checked 13 Sep 2026

Hybrid Context Engine

A platform that turns an organisation’s documents, recordings and databases into permission-aware context that any LLM agent can use over MCP. It is designed around the hardest questions it has to answer: the ones that need a database and a document at the same time.

Scale assumed10⁶–10⁷ documents (≈10⁷–10⁸ pages), tens of databases, one organisation.
Hosting assumedYour cloud VPC. Frontier LLM APIs are allowed under enterprise terms.
Still openWhether document content may go to third-party embedding or parsing APIs. Each layer names an API default and a self-hosted equivalent.
Out of scopeWrite actions. The engine is read-only by design (§6.2).

2The questions decide the architecture

“Answer questions across the corpus” is at least eight different problems. Only the first three are what most teams build when they say RAG. The rest need exact matching, deterministic computation or an explicit plan. An engine that only offers top-k semantic search makes the agent fake those with snippets, and that is where confident wrong answers come from.

#ClassExampleWhat actually answers itTools (§5.6)

4Aggregate over documents“How many supplier contracts auto-renew in Q4?”A table: pre-extracted fields, or a capped map/filter over a filtered set. Never top-k.browse query_table

7Sense-making“What themes dominate complaints this quarter?”Map-reduce over a filtered, sampled set, with the sample disclosedask

The evidence for splitting classes 4–6 out of “RAG”:

  • FinSheet-Bench: frontier models score 89% on simple spreadsheet lookups but 19.6% on percentile-style operations. The authors conclude that reliable systems must “separate document understanding from deterministic computation.”
  • Data Agent Benchmark (54 enterprise queries across four DBMSs): the best model reached 38% pass@1. 85% of failures were wrong implementation or planning, not wrong tables, and every agent used regex for text extraction.
  • HybridDeepResearch (Snowflake, June 2026) names the hybrid failure modes. In the salience trap, agents drop the database anchor when a high-ranked text result looks relevant. In anchor dropout, text findings never become SQL predicates. The third is a skipped final intersection.

3Principles

These eight rules generate most of the component choices below. Each is tied to evidence rather than taste.

Many interfaces, not one retriever

Agents do better when they can search by meaning, match exactly, filter and count, read with navigation and run SQL. A single top-k endpoint pushes every question through the one channel it fits least.

Evidence: direct corpus interaction (grep-style access beat sparse, dense and reranked retrieval on BRIGHT and BrowseComp-Plus); ViDoRe V3 (text and visual channels are complementary).

Compute, don’t generate

Counting, summing, ranking and joining happen in SQL or DuckDB. The model plans, reads and explains.

Evidence: FinSheet-Bench; DAB (pushing aggregation into SQL beat post-processing in Python).

Databases stay where they are

Index their metadata, semantics, values and query history. Query the rows live, as the user. Freshness is free, regulated rows get no second copy, and native row-level security keeps working.

Reasoning; see §5.5 for the execution path.

Indexes are disposable; the lake is not

Keep parse output, chunks and embeddings in a versioned lake so any index can be rebuilt without touching the sources. Re-crawling is the slowest, most rate-limited step, and some sources forbid it.

Evidence: Mistral shipped four OCR generations in 15 months; the OmniDocBench leader changed again on 11 Sep 2026.

Permissions are enforced twice, by the engine

Filter inside every index channel, then re-check the final candidates against the source of truth. The model never sees content the user can’t open, so no prompt can talk it into leaking.

Pattern: SpiceDB pre- and post-filtering; see Figure 2.

Pre-index by default, federate by exception

An index gives consistent ranking and speed. Federation is for sources whose terms, privacy or volatility demand it.

Evidence: Slack’s 2025 API terms forbid third-party persistent indexes; MCP-only federation is slower and less relevant.

Measure on your data before choosing

Build the golden set before the features. Leaderboards are a prior, not a verdict.

Evidence: MTEB’s top three placed 5th, 7th and 2nd on one legal in-domain set; CIDR 2026 text-to-SQL annotation audit.

Treat retrieved content as hostile

Any document can carry a prompt injection. Keep the engine read-only with no egress, label provenance, and never let retrieved text change a plan.

Evidence: CaMeL (separating control flow from data flow); indirect injection via MCP.

4System at a glance

Read it bottom-up for the write path and top-down for the read path. Documents are copied, parsed and stored once in the lake, and every index above the lake is a projection that can be rebuilt. Databases never enter the lake: only their metadata reaches the catalog, and their rows are queried live.

5Layers

Each layer ends in a decision record with four parts: what we pick, why, what we rejected, and the trigger to revisit.

5.1Connect & sync

Decision
A connector SDK with one contract for every source, running as Temporal workflows (one per document version), with Ray Data for bulk backfills. Databases get metadata connectors, not row copies. Sources whose terms forbid indexing are federated at query time.
Why
Durable per-document workflows give you retries, rate-limit-aware windows and heartbeats for long crawls, and trace every failure back to one document. Rapidflare ran a million-document agent ingestion this way. Ray Data streams GPU-heavy parse and embed work for 10⁷-page backfills. One contract means ACLs travel through the same code path as content, so the two can’t drift apart.
Rejected
  • Federating everything over MCP. It is slower, ranking can’t be fused across heterogeneous APIs, and quality depends on which system happens to hold the answer (LlamaIndex).
  • Nightly full crawls. They make the ACL drift window a full day.
Revisit when
A source offers only live search (federate it), or event volume outgrows per-document workflows (move that source to a Ray-only batch lane).

The contract

// every connector implements the same five calls
changes(cursor)   → [{ id, version, op: upsert|delete|acl }], next_cursor
fetch(id)         → bytes + source metadata + deep link
acl(id)           → { principals: [user:, group:, domain:], link_sharing }
principals()      → users, groups, memberships        // for the principal graph
identity_map()    → source user id ↔ IdP identity
  • Three connector kinds. Indexed content covers SharePoint and OneDrive through Graph delta queries, Google Drive through its changes feed, Box, Confluence, object stores, file shares and email. Structured metadata covers Postgres, MySQL, Snowflake and the rest: schemas, comments, statistics, distinct values of low-cardinality columns, query history and row-access policies. Federated covers sources searched live, such as Slack through its Real-time Search API.
  • Freshness. Change feeds and object events give minutes-level freshness. A weekly reconciliation crawl catches missed events and ACL drift. Deletions and ACL changes skip the queue on a priority lane with its own SLO (proposed: p99 under 5 minutes).
  • “New kinds of databases keep appearing.” Supporting one means writing two adapters: a metadata extractor, and a read-only executor over ADBC, Arrow Flight SQL, JDBC or an existing Trino connector. The catalog, semantic layer and tools don’t change.
  • Reuse before writing. Enumeration and fetch code exists in Airbyte (600+ connectors), Onyx (50+ with permission sync) and Airweave (50+ integrations). Own and test ACL extraction for your top sources; that is where connectors quietly go wrong.

5.2Understand: parsing, audio, spreadsheets, chunks

Decision
Docling is the conversion hub and intermediate representation (IR) for every format. A router sends only scanned or layout-hard pages to PaddleOCR-VL-1.6 on vLLM. Mistral OCR 4 is the fallback for pages that fail validation. Audio goes through ASR with word timestamps and speaker diarization.
Why
Docling (MIT, under LF AI & Data) reads PDF, DOCX, PPTX, XLSX, HTML, EPUB, EML/MSG, images, WAV/MP3, WebVTT and video into one document model. It also ships an MCP server and a service mode. PaddleOCR-VL-1.6 (Apache-2.0, released 28 May 2026) scores 96.3 on OmniDocBench v1.6. On the same board Gemini 3 Pro scores 92.9 and GPT-5.2 scores 86.6. Its predecessor measured 1.62 pages/s on one A100 with vLLM. Born-digital Office files need no OCR at all, so the router saves more money than any model choice.
Rejected
  • MinerU2.5-Pro as the default. It is strong (95.75), but its licence requires a commercial agreement above US$20M monthly revenue.
  • One VLM for every page. That spends GPU time on files that already have perfect text.
  • Letting OmniDocBench decide. It is 1,651 pages weighted toward academic, Chinese and English layouts, and olmOCR-bench is ~56% academic papers. Neither looks like your invoices.
Revisit when
Every quarter. TeleOCR (96.91) and OvisOCR2 (96.47) topped the board on 11 Sep 2026. Mistral OCR 4 (23 Jun 2026; $2 per 1,000 pages in batch; single-container self-host) and Cohere Parse 5 (27 Aug 2026) are recent entrants. Re-run your own page set.
  • Router. Route by MIME type plus a probe. For PDFs, check text-layer quality (coverage, garbage ratio) and layout signals (tables, multi-column, forms). Good text with a simple layout takes the fast path; everything else goes to the VLM. Images get a VLM parse and a caption.
  • IR. Sections contain blocks (paragraph, table, figure, list, formula, code). Each block carries provenance: page, bounding box and character offsets, or a time range for media. Page images are rendered and kept, both for the visual channel and for answering with the page itself. On ViDoRe V3, page-image context beat text context 64.7% to 62.3% when the right pages were given.
  • Spreadsheets. Detect the table regions on each sheet (a sheet often holds several). Each table becomes a Parquet/Iceberg “document table” queryable by DuckDB. A text card (sheet name, headers, units, sample rows, statistics) makes it findable. Formulas are kept as metadata. The model finds the table; SQL does the arithmetic.
  • Chunking. Chunk by structure: paragraph groups of about 300–800 tokens, never crossing a section boundary, with each table as its own chunk and its header row repeated. Prefix every chunk with a context header: title › section path › caption · date · source. That “enriched title” variant is the cheap win in an Aug 2026 study covering 10K–10M documents. The same study found LLM-contextualised and semantic chunking rarely gave consistent gains, for 5–50× the processing time. Anthropic’s contextual retrieval (−49% failed retrievals, −67% with reranking) is still worth a bake-off on low-context fragments such as slides, spreadsheet cards and email replies, but not as a default.
  • Enrichment. Tag document type, language, effective and expiry dates, and entity mentions (people, organisations, products, identifiers). A small model writes a short document card.
  • Extraction tables. For high-volume document types (contracts, invoices, purchase orders), define one schema per type. An LLM fills it with a citation (page and box) and a confidence for each field. Low-confidence fields go to a review queue. These tables are what make class-4 and class-6 questions exact.
  • Audio. Choose by accuracy on your own recordings; names and jargon dominate business audio. The API default is AssemblyAI Universal-3.5 Pro, which reports lower entity error and cpWER than ElevenLabs Scribe v2 (vendor-reported). To self-host, use Granite Speech 4.1 2B (Apache-2.0, 5.33% mean WER, keyword-list biasing) or Qwen3-ASR-1.7B (52 languages), with pyannote Community-1 for diarization. Feed the entity store’s names into keyword biasing, and map diarised speakers to people from calendar metadata where available.
  • Parser evaluation. Take 50–200 of your own pages per document family, with gold markdown and tables, and score each element type: text, table structure and reading order.

5.3Context lake

Decision
Raw objects live in versioned S3. Everything derived lives in Apache Iceberg v3 tables: IR, chunks, embeddings, page-image references, extraction tables, entities and pipeline versions. Every index is a rebuildable projection keyed by (doc_id, doc_version, pipeline_version).
Why
Parsers, embedders and rerankers will each be replaced several times over this platform’s life. Iceberg v3 became production-ready with Iceberg 1.11.0 (19 May 2026) and is GA on Snowflake since 7 May 2026. It adds deletion vectors for fast deletes and row lineage for native change feeds, which the projection jobs consume to update indexes incrementally. The same tables are readable from Snowflake, Databricks, Trino and DuckDB, so extraction tables join directly with warehouse data.
Rejected
The index as the system of record, which makes every model upgrade a re-crawl. A vector database as the lake, which can’t serve SQL joins.
Revisit when
Multimodal ML (fine-tuning on page images, dataset curation) becomes a main workload. Lance format has better random access for that, and Milvus 3.0 (Jul 2026) already searches Lance, Iceberg and Parquet in place.
  • Model upgrades. Build the new projection behind a blue/green index alias, shadow-evaluate it on the golden set, then flip. Voyage 4’s shared embedding space lets you change the query-side model without re-embedding documents.
  • Deletion. A tombstone propagates to every projection and cache. The lake keeps an audit record, not the content. Legal hold uses S3 Object Lock.

5.4Projections: index, pages, entities, catalog

Decision
OpenSearch 3.x holds three indexes. The chunk index has BM25 with language analyzers, dense vectors with 1-bit BBQ quantisation and rescoring, ACL principal lists, metadata and facets. The other two are the visual page index and the document-card index.
Why
Enterprise questions depend on exact tokens: part numbers, clause names, acronyms, people. That makes lexical search a primary channel, not a fallback, and Lucene’s analyzers, phrase and regex queries are the most mature available. ACL filtering is a terms filter over principal IDs, which Lucene engines have run at scale for over a decade. browse needs aggregations. OpenSearch 3.6 (10 Apr 2026) added Lucene BBQ at 32× compression (recall above 0.95 with oversampling on Cohere-10M). Document- and field-level security ship in the Apache-2.0 build, and managed offerings exist. Onyx, an open-source enterprise search product with the same connector-and-permissions problem, moved its whole index from Vespa to OpenSearch in v3–v4 (Mar–Apr 2026). It hasn’t said why, so treat that as a signal, not proof.
Rejected
  • Elasticsearch 9.x. Its hybrid tooling is as good or better (retrievers, semantic_text, and Jina models since Elastic acquired Jina AI in Oct 2025), but document-level security sits in paid tiers. Pick it if you already license Elastic.
  • Vespa. The most capable ranking engine, with multi-phase tensor ranking and in-engine ColPali at billions of pages. The capabilities where it leads are the ones this design puts elsewhere: final ranking goes to a cross-encoder, and visual retrieval uses single vectors.
  • turbopuffer. Built on object storage, cheap at scale, with BM25, vectors and filters; Cursor, Notion and Anthropic run on it. It has no aggregations or multi-vector, you build second-stage ranking yourself, and a SaaS vendor becomes a processor of the whole corpus.
  • Qdrant, Milvus. Strong vector engines, but their lexical analysis and facets are less mature than Lucene’s, and lexical is a primary channel here.
  • Postgres only (pgvector or VectorChord, plus pg_textsearch or ParadeDB). The simplest stack under ~10⁷ chunks. But its BM25 extensions are one to two years old, and this platform needs BM25, quantised ANN, large ACL filters and facets together at 10⁸ rows. That combination is where Lucene engines have the longest production record.
Revisit when
You pass ~10⁹ chunks or need learned ranking over many features: go to Vespa (now with a Kubernetes operator). A late-interaction visual model beats single vectors by a margin you care about: go to Vespa or Qdrant multivector. The corpus turns out to be under ~10⁷ chunks: go Postgres-only. SaaS is acceptable and cost dominates: go to turbopuffer.

Chunk record

chunk {
  id, doc_id, doc_version, source, url,
  context_header, text,                 // BM25 over both
  vec_text: bbq_1bit(1024),             // dense channel, rescored from disk
  acl_principals: [keyword],            // user:…, group:…, domain:…
  acl_version, sensitivity_label,
  doc_type, lang, entity_ids: [keyword],
  valid_from, valid_to, updated_at,     // class-8 questions
  provenance: { page, bbox } | { t_start, t_end }
}
  • Visual page index. One vector per rendered page, covering slides, charts, scans and diagrams. On ViDoRe V3 (≈26,000 enterprise page images, 10 domains), the best visual retriever scored 59.8 nDCG@10 against 51.0 for the best text retriever. Giving the generator the top five from each answered 54.7% of hard queries, more than either channel alone. The default model is Qwen3-VL-Embedding-8B (Apache-2.0), which its authors report as comparable to ColPali-style multi-vector models at far lower cost. Those models store about a thousand 128-dim vectors per page. On Google Cloud, Gemini Embedding 2 (GA 22 Apr 2026) is the alternative; it puts text, image, audio, video and PDF in one space.
  • Document cards. One record per document (title, summary, owner, dates, type, entities). This is what browse returns, and a coarse first stage for long documents.
  • Entity store (Postgres). Tables for entities (canonical ID, type, names, aliases), mentions (chunk, span), links to structured keys such as snowflake:crm.customers.id=4812, and typed relations where extracted. Linkage uses Splink (probabilistic record linkage on DuckDB or Spark, 100M+ records), with an LLM deciding only the uncertain pairs. LLM-only matching costs 100–1,000× more at production volume (vendor analysis). This is the bridge that makes class-6 questions joinable.
  • Why not GraphRAG now. In a systematic comparison, plain RAG beat Microsoft’s community GraphRAG on single-hop questions (64.78 vs 63.01 F1). On MultiHop-RAG the two tied once RAG got the same token budget (69.33 vs 69.01); GraphRAG had been using 9,770 tokens per query against 3,631. Graphs earn their cost on relationship-heavy and global questions. So build the entity layer now, which is cheap and needed for hybrid anyway. Use query-time community summarisation (LazyGraphRAG-style, about 0.1% of GraphRAG’s indexing cost) for class-7 questions. Add a graph database only when traversal queries recur. Note that Kùzu was archived in Oct 2025 and continues as the LadybugDB fork.
  • Catalog and semantic layer. DataHub ingests schemas, descriptions, lineage and query history, and already exposes search, lineage and schema tools over MCP. Three things go on top:
    • embeddings over tables, columns and metrics for schema linking;
    • a value index of distinct values in categorical columns, so “Acme” resolves to 'ACME Corp Inc.';
    • golden queries: verified SQL for recurring questions, mined from query logs and reviewed.
    Metrics are defined once in Apache Ossie format, with MetricFlow (Apache-2.0) as the reference implementation. Ossie was formerly OSI: v1 shipped in Jan 2026 and it entered the Apache Incubator in Jul 2026. Where Snowflake is the warehouse, Snowflake semantic views are the alternative.

5.5Serving: retrieval, SQL and the planner

One API sits in front of three execution paths. Figure 2 is the inside of search, the call every agent makes most.

Retrieval

  • Latency budget. In-engine retrieval takes tens to low hundreds of milliseconds. The top API rerankers add 265–614 ms (Agentset, Feb 2026). The target for search is p95 ≈ 1 s.
  • Reranker. Cohere Rerank 4 Pro or zerank-2 (ELO 1629 and 1638, the top two on that board). On ViDoRe V3, a text reranker (zerank-2) added +13.2 nDCG@10 to the text pipeline, while a visual reranker added +0.2. So rerank the text channel, and rerank visual hits by their page text. To self-host, use Qwen3-Reranker (Apache-2.0). The 8B model took 4.7 s on the same board, so size down and batch. zerank-2’s open weights are CC-BY-NC: use the API or buy a commercial licence.
  • Text embeddings. Run a bake-off on the golden set between three candidates:
    • voyage-4-large for indexing with voyage-4-lite for queries. The vendor reports +3.87% over Gemini Embedding 001 and +8.20% over Cohere Embed v4 on RTEB.
    • Gemini Embedding 2.
    • Qwen3-Embedding-8B (Apache-2.0), for content that can’t leave the VPC.
    Don’t pick from MTEB rankings; see §3.

Structured path

  • describe_data returns only the relevant slice of the schema: candidate tables and columns with descriptions, join paths, matching values from the value index, related metrics and golden queries. On the Data Agent Benchmark, top agents spent about 20% of tool calls exploring, and both less and more hurt. Exploration should be a tool, not a hope.
  • query_metrics compiles through the semantic layer, so covered questions are deterministic. dbt’s April 2026 re-run on modelled data found:
    • Claude Sonnet 4.6: 90.0% with text-to-SQL, 98.2% through the semantic layer;
    • GPT-5.3 Codex: 84.1% with text-to-SQL, 100% through the semantic layer.
    The semantic layer fails loudly when a question isn’t covered; text-to-SQL returns a plausible wrong number.
  • run_sql is the fallback, and every step is a guard:
    • parse and validate (read-only statements only);
    • check cost with EXPLAIN, and cap rows and time;
    • execute at the source with the user’s identity: OAuth to Snowflake, database roles and row-level security in Postgres;
    • where identity passthrough is impossible, use a service role with an explicit policy check and the human named in the audit record.
    Results come back with the SQL, the source and the as-of time; that is the citation for a number. Answers built this way are labelled as unverified SQL.
  • Cross-database joins go through Trino only when a question genuinely spans two systems. Starburst now treats MCP agents as scoped service accounts. Otherwise, push the query down to the one source that holds the data.

The planner (ask) and hybrid questions

  • The plan comes from the trusted question only. Retrieved text is data and can’t add tool calls; this is the CaMeL pattern. It also enforces the ordering that stops the salience trap.
  • Sufficiency before synthesis. The validator checks the intersection and whether the evidence is enough to answer. Google reports up to 34% accuracy gains on factuality datasets from a sufficient-context agent (vendor-reported, Jun 2026). When evidence is short, the answer says what is missing.
  • Aggregates without an extraction table. Run a semantic map/filter over a candidate set narrowed by metadata, with a hard budget in documents and dollars, and disclose coverage (“checked 180 of 1,240 contracts”). LOTUS, DocETL and Palimpzest are the reference designs.
  • Keep bulky results out of the model’s context. An optional analyze tool runs Python/DuckDB over tool outputs in a sandbox with no network access. This is the code-execution-with-MCP pattern; Anthropic measured 150,000 → 2,000 tokens in its example. It widens the attack surface, so it ships last and never gets egress.

5.6Agent interface

Decision
An MCP server on the 2026-07-28 specification is the primary interface. A REST/OpenAPI mirror serves non-MCP clients. The ask planner can also be published as an A2A agent.
Why
MCP is the protocol the major agent hosts speak. Since Dec 2025 it has been governed by the Linux Foundation’s Agentic AI Foundation, which A2A has also joined. The July 2026 revision changes four things that matter here:
  • No initialize handshake or session IDs, so any request can land on any server instance behind a plain load balancer.
  • Mcp-Method/Mcp-Name headers let the gateway route and rate-limit per tool without parsing bodies.
  • List results carry ttlMs for caching.
  • Multi Round-Trip Requests handle “which Acme did you mean?”, and the Tasks extension handles long ask runs by polling.
Rejected
A custom SDK per agent framework: the M×N integration problem MCP exists to remove.
Revisit when
Other agents need to delegate whole research tasks: publish ask as an A2A agent card.

  • Auth. OAuth 2.1 with protected-resource metadata (RFC 9728), resource indicators (RFC 8707), Client ID Metadata Documents (dynamic client registration is deprecated in 2026-07-28) and RFC 9207 issuer validation. Every audit record names both the human and the agent.
  • Tool design. Return IDs, titles, snippets and citations, and let the agent fetch what it needs: the “just-in-time” loading in Anthropic’s context engineering guide (Sep 2025). Keep tools non-overlapping. If an engineer can’t say which tool fits a question, the model can’t either.

6Cross-cutting planes

6.1Permissions

  • Identity map and principal graph. Map every source user to an IdP identity. Build a principal graph of users, groups (nested groups flattened into precomputed transitive memberships), domains, and link-sharing, modelled explicitly.
  • Early and late binding, as in Figure 2. Chunks store principal IDs, and queries filter by the user’s expanded principal set. Final candidates are bulk-checked against the source before anything is returned.
  • Leak paths teams forget:
    • Facet counts and “N results hidden” messages reveal that documents exist, so compute facets after filtering and never show hidden counts.
    • Generate snippets only after the late check.
    • Key caches by a hash of the principal set.
    • lookup_entity returns only mentions the user can see.
  • Complex inheritance. When sources need inheritance or custom sharing rules across systems, model them once in SpiceDB rather than in each connector. Use LookupResources for pre-filtering and bulk checks for post-filtering. AuthZed’s Materialize precomputes permission sets, but is early access.
  • Databases. Prefer identity passthrough. Where access runs through a service role, the audit record names the human.

6.2Security

The engine combines two legs of the “lethal trifecta”: private data, and untrusted content (any document can carry a prompt injection). The third leg, an exfiltration channel, lives in whatever other tools the client agent holds. The engine can’t remove that leg, so it makes itself a poor place to start an attack.

  • Read-only by design. No write tools, and no outbound network from the engine or its sandbox.
  • Provenance on every result: source, author and sensitivity label. The planner treats retrieved text as data (CaMeL-style separation of control and data flow).
  • Injection scanning at ingestion. Chunks with instruction-like content are flagged, labelled and down-ranked, not silently deleted.
  • Sensitivity labels travel with chunks. Policy can withhold highly confidential content from specific clients or agents.
  • Volume anomaly detection on fetch patterns per identity, to catch bulk extraction.
  • Supply chain. Pin and hash-verify dependencies and images, and keep publishing credentials away from CI jobs that run third-party tools. The case study is the LiteLLM compromise of 24 Mar 2026: malicious 1.82.7 and 1.82.8 releases were live on PyPI for about 40 minutes, traced to a compromised Trivy step in CI.

6.3Models and gateway

  • All model calls (LLMs, embedders, rerankers) go through one gateway for routing, keys, budgets and tracing. Either self-host a pinned, hash-verified build or use your cloud’s native gateway.
  • A small, fast model handles query analysis, enrichment and document cards. A frontier model is used only for ask planning and synthesis. The engine stays model-agnostic, and internal calls are pinned to versions.
  • Embedders and rerankers are versioned services. Changing a version triggers the evaluation gate (§6.4) and a blue/green projection (§5.3).

6.4Evaluation and observability

  • Golden set before features. Collect at least 50 real questions per class (§2), each with gold evidence: document and page, or verified SQL and its result. Real questions come from pilot users; synthetic ones must be human-verified. The CIDR 2026 audit found annotation errors in 52.8% of BIRD Mini-Dev and 66.1% of audited Spider 2.0-Snow examples, enough to move rankings by up to three places.
  • Metrics per stage:
    • parser element accuracy;
    • retrieval recall@k and nDCG, and rerank lift;
    • answer correctness, citation precision and groundedness;
    • SQL execution accuracy;
    • abstention quality;
    • ACL red-team pass rate and revocation lag.
  • CI gate on every parser, embedder, reranker, prompt or model change.
  • Tracing. Emit OpenTelemetry GenAI spans for agents, model calls and MCP. The conventions are still in Development status and moved to their own repository on 12 Jun 2026, so pin the version. Send traces to Langfuse, self-hosted; it is open source and was acquired by ClickHouse in Jan 2026.
  • Online signals: user feedback, citation clicks, the rate of “insufficient evidence” answers, and latency and cost per tool.

What the numbers say. Re-embedding the corpus is cheap. Re-parsing it is not, and re-crawling it may be impossible. That ordering is why the lake stores parse output, why the router matters more than the parser, and why the index choice hinges on quantisation rather than raw ANN speed.

The A100 figure was measured for the original PaddleOCR-VL on vLLM 0.10.2; version 1.6 keeps the same ~1B architecture line, but re-measure on your hardware. The embedding figure uses one list price to show scale; others will differ.

8What we deliberately didn’t choose

  • A vector database as the retrieval system. Vectors are one of three channels. Identifiers need lexical search, and counts need tables (§2).
  • A full GraphRAG index up front. It matches plain RAG once token budgets are equal, and costs far more to build. Build the entity layer instead (§5.4).
  • Text-to-SQL on raw schemas as the metrics path. It produces plausible wrong numbers. The semantic layer comes first (§5.5).
  • Stuffing long context instead of retrieving. All 18 models in Chroma’s context-rot study degraded as input grew, and a 10⁸-page corpus doesn’t fit anyway.
  • Federating every source over MCP. It is slow and can’t be ranked across sources. Use it only where it’s required (§5.1).
  • LLM-contextualised chunking everywhere. The gains were rarely consistent at scale, for 5–50× the processing time (§5.2).
  • Multi-vector ColPali embeddings for every page. About a thousand vectors per page. Single-vector visual embeddings plus a text reranker capture most of the gain (§5.4).
  • Picking components from leaderboards. The legal-set MTEB reversal, OmniDocBench’s document mix and the text-to-SQL annotation audit all point the same way (§3, §6.4).

11Open questions that change the design

  1. Can document content go to third-party model APIs for embedding, parsing and reranking? If yes, the API defaults above stand. If no, swap in Qwen3-Embedding, Qwen3-VL-Embedding, Qwen3-Reranker, PaddleOCR-VL and Granite Speech, which means one more GPU pool to operate.
  2. What is the real scale? Documents, pages, audio hours, databases, tables and concurrent users. Under ~10⁷ chunks, Postgres-only is simpler; past ~10⁹, look at Vespa.
  3. Where do documents live? Microsoft 365, Google Workspace, file shares, something else. This sets connector order and the shape of the ACL model.
  4. Is there a semantic layer or dbt project today, and is Snowflake the main warehouse? This decides between MetricFlow/Ossie and Snowflake semantic views.
  5. What compliance applies? GDPR, HIPAA, residency, deletion SLAs, retention, legal hold. These set the revocation SLO, the regions, and whether audio may be stored at all.
